# ADR-0020 Codex 分叉线程复制历史:用第二把键去重,而不是改 event_id

状态:已采纳(2026-07-31)

## 背景

ADR-0009 的「实现落地修正」第六条记下一件当时不解决的事:恢复会话时 Codex 会把
旧线程的 `token_count` 行逐字复制进新 rollout,而 `event_id` 由 rollout id + 时间戳 +
序号构成,于是同一次生成产出两个不同的 id,去重拦不住,这部分用量被计两次。

这条 ADR 处理它。**动手前先把现象重测了一遍,性质与原判断不同**,下面第一节就是更正。

## 一、事实更正:不是「恢复会话」,是「分叉线程」

全量扫 610 个 rollout(33,445 条会入库的用量事件),`turn_id` 跨文件出现的有 99 个。
但其中 5 个是假的:

| `turn_id` 形态 | 数量 | 跨文件出现 | 性质 |
|---|---|---|---|
| UUIDv7(`019f6fb0-ec56-…`) | 3,315 | 94 | 真复制 |
| 整数计数器(`"2"`、`"3"`…) | 5 | 5 | **假阳性** |

整数那 5 个来自 `source: mcp` 的会话 —— 那种会话的 `turn_id` 是会话内自增计数器,
`"2"` 在 13 个互不相关的文件里各自出现一次,不是同一次生成。**`turn_id` 因此不是
全局唯一的**,这一点直接决定了下面键的构造。

剩下 94 个真复制,来源全部可指认。逐字对比 45 个涉事文件的 `session_meta`:

```
rollout-2026-07-17T06-47-59-019f6fb0-….jsonl   source=vscode  thread_source=user
rollout-2026-07-28T23-13-26-019fabdc-….jsonl   source=vscode  thread_source=user
                                               forked_from_id=019f6fb0-…
```

```
rollout-2026-05-27T09-26-24-019e670a-….jsonl   source=cli     thread_source=user
rollout-2026-05-27T10-18-55-019e673a-….jsonl   thread_source=subagent
                                               forked_from_id=019e670a-…
                                               source.subagent.thread_spawn.parent_thread_id=019e670a-…
```

两类都是**分叉**:用户手工 fork 一条线程,或 Codex 派生 subagent 线程。派生出来的
文件把父线程**从头到尾整段复制成自己的前缀**,然后才写自己的新内容。复制的部分:

- `task_started` / `task_complete` 的 `turn_id`、`started_at`、`completed_at`、
  `duration_ms`、`time_to_first_token_ms` —— 逐字保留;
- `token_count` 的 `last_token_usage` / `total_token_usage` —— 逐字保留;
- **只有行时间戳被换成刷盘时刻**。实测 fork `019fabdc` 的 4,300 余行前缀全部落在
  `2026-07-29T03:13:26.378Z`–`.450Z` 这 72 毫秒里,而它们原本横跨 7 月 17 日到 28 日。

也就是说 ADR-0009 那条注记说的现象是真的,但它的名字错了:**触发复制的是分叉,不是
恢复**;而且 subagent 也会触发,不只是人工恢复。`internal/parser/codex/parser.go` 里
「Codex 恢复线程开新 rollout 文件,不复制旧 token_count 行」那句注释同样与实测不符。

### 影响量

按解析器实际会入库的口径(`deltaUsage` 语义,累计值未推进的行本来就跳过):

| | 值 |
|---|---|
| 会入库的用量事件 | 33,445 |
| 其中是复制副本的 | **845**(2.53%) |
| 涉及的生成次数 | 647(一个 turn 可被复制进多个 subagent) |
| 重复计入的 output token | **629,518 / 20,169,027 = 3.12%** |
| 重复计入的 input token | 105,818,856 / 4,211,822,218 = 2.51% |
| 承载副本的文件 | 10 个,**全部**带 `forked_from_id` 或 `parent_thread_id` |
| 副本与原件的用量字段不一致的组 | **0 / 647** |

(ADR-0009 记的是 82/1027 个 turn、只扫了近 200 个 rollout;本次全量扫描的
94/3,320 与之不矛盾,是覆盖范围不同。)

## 二、为什么现有 event_id 拦不住,以及为什么不能靠改它来拦

`cx:sha1(rolloutID | 时间戳 | 文件内序号 | usage)`。副本换了 rollout id,也换了时间戳,
所以两份必然产出不同的 id。同一批数据实测:现行方案在 33,445 条上产出 33,445 个不同的
键,**一次都没有合并过任何东西** —— 它在这件事上不是判错了,而是构造上就没有能力判对。

顺理成章的修法是换 `event_id` 的依据,让两份副本产出同一个 id。**这条路被否决**,
理由不是构造不出这样的键(第三节就构造出来了),而是**历史数据无解**:

- 库里 33,610 条 codex 事件用的是旧 id。换依据之后重扫会用新 id 再插一遍,**全库
  codex 重复**,比现在这 3.12% 严重一个量级;
- 想避免就得做一次性 id 迁移。迁移要么按内容重算(库里没有 `turn_id`、没有
  `total_token_usage`,重算不出来),要么让解析器同时产出新旧两个 id、由存储层把
  旧 id 的行改写成新 id。后者能做,但代价是:`event_id` 这一列从此可被改写、
  agent 协议要多带一个 legacy 字段、且解析器必须**永远**保留一份旧 id 的计算逻辑
  (否则没跑过迁移的库再也接不上)。为了一个 3% 的问题,把 ADR-0004 的主键从
  「不可变」降级为「可迁移」,不划算;
- 而且迁移只覆盖日志还在的那部分。N6 要求数据入库后独立于源日志生命周期,
  没被迁移到的行会永久停在旧 id 上,新旧两套 id 长期并存。

**所以 `event_id` 的生成依据不变。** ADR-0004 的铁律原样成立,`TestEventIDsStable`
钉的那三个字面量一个都不动。

## 三、决策:加第二把键 `dedup_key`

在 `events` 表上加一列 `dedup_key`,配一个**部分唯一索引**;`event_id` 仍是主键。
两把键都是全局唯一约束,谁先撞上都拦得住:

- `event_id` 回答「这条**日志行**见过没有」—— 防重扫、防双通道重传;
- `dedup_key` 回答「这次**生成**记过没有」—— 防同一次生成被复制进第二个文件。

只有 codex 解析器填 `dedup_key`。claude-code 不需要:`message.id` 本来就随副本一起
被复制,ADR-0004 在那一侧成立的原因正是这个。proxy 不需要:它没有副本。列是通用的,
生产者暂时只有一个。

### 3.1 键的构造

```
dedup_key = "cxg:" + sha1(turn_id | total_token_usage 的六个字段)[:12]
```

`turn_id` 取所属 turn 的(`task_started` 按文件位置括起,与 ADR-0009 同一套归属),
**且仅当它是 UUID 时才产出键**;不是 UUID 就留空,退回只靠 `event_id` 去重。

三条依据,都用真实数据验过,不是设计推断:

**(a) 跨文件稳定。** 分叉复制的是原样的字节,`turn_id` 与 `total_token_usage` 都在
复制范围内,只有行时间戳被改写 —— 而键里一个时间戳都没有。647 个碰撞组里
**0 组的用量字段不一致**,复制是逐字的。

**(b) 同一文件内绝不误合。** `total_token_usage` 是线程内单调累计值,而解析器本来
就跳过累计值未推进的 `token_count` 行(ADR-0004 已有的规则),所以一条线程里每次
生成的累计值互不相同。实测:33,445 条产出 32,259 个键,**同文件碰撞 0 次**,
647 次碰撞**全部跨文件**。

**(c) 跨会话绝不误合。** 这一条是 `turn_id` 必须是 UUID 的原因。同样的实测里,
只用 `total_token_usage`(不带 `turn_id`)会多出 **1 次同文件碰撞** —— 两次不同的
生成恰好累计到同一个数。而只用 `turn_id`(不带累计值)在整数 `turn_id` 那批上会把
13 个无关会话的 `"2"` 合成一条。两者都是**少计**,方向比多计更坏,因为看不出来。
UUIDv7 是构造上全局唯一的,会话内自增计数器不是 —— 键只建立在前者上。

### 3.2 覆盖率与遗漏的性质

| | 事件数 | 占比 |
|---|---|---|
| 有 UUID `turn_id`,产出键 | 33,104 | **99.0%** |
| `turn_id` 是整数计数器 | 165 | 0.5% |
| 完全没有 `turn_id`(0.136.0 旧版不写 `task_started`) | 176 | 0.5% |

341 条没有键。**其中在分叉文件里的:0 条。** 也就是说这 1% 的遗漏与本问题不相交 ——
没有键的会话不会被分叉,也就没有副本要拦。这是实测的事实,不是运气:整数 `turn_id`
只出现在 `source: mcp` 的会话里,那种会话是一次性的,不派生 subagent 也不被 fork。

还有 5,108 次生成只存在于某个分叉文件内部(subagent 自己干的活,父文件里没有)。
键对它们不产生碰撞,原样入库 —— **去重不会吃掉分叉线程自己的用量**,这是必须
明确的边界。

### 3.3 冲突消解:留下时间戳早的那条

两条记录撞上同一个 `dedup_key` 时,**保留 `ts` 小的那条,删掉另一条。**

判据是数据本身而不是到达顺序,因此与扫描顺序无关 —— 无论先扫父文件还是先扫分叉
文件,收敛到同一个结果。它同时是**语义上正确**的那条:分叉必然发生在被它复制的生成
之后,副本的行时间戳是分叉时的刷盘时刻,所以原件的 `ts` 恒小于副本的。647 个碰撞组
里没有一组的两份副本时间戳相同(0 次并列),实测差距动辄以小时/天计
(例:原件 `2026-05-27T01:26:39.830Z`,副本 `2026-05-27T02:28:50.744Z`)。

**留错了会怎样**:副本的 `ts` 是虚构的,留下副本等于把 7 月 17 日的用量画到 7 月 29 日。
这就是不能简单用 `INSERT OR IGNORE`「谁先到谁赢」的原因。

被删的那条不携带任何独有信息:用量字段逐字相同(0/647 组不一致),而派生字段
`gen_ms` / `ttft_ms` 在副本上恒为 0 —— ADR-0009 的实现已经拒绝给回放 turn 量区间
(行时间戳与 `completed_at` 差超阈值就不给),所以副本本来就是空的。

### 3.4 历史数据:不重建,不迁移,一次重扫收敛

因为 `event_id` 没变,已入库的 33,610 条 codex 事件**全部原地不动**,不存在新旧 id
并存的问题,也就没有第二节说的那些代价。重扫时:

1. 每条事件先按 `event_id` 走原有的 `INSERT OR IGNORE`;
2. 命中已有行时,把 `dedup_key` 回填上去 —— 这就是 ADR-0009 已经确立的
   「只补派生列、绝不碰计数列」的 UPSERT 模式,`gen_ms` 当初也是这么回填的;
3. 回填时撞上唯一索引,说明同一次生成在库里已有另一条行 —— 按 3.3 消解,删掉
   `ts` 大的那条。

一次 `serve -rescan` 就把 845 条副本清掉。这 845 条的原件与副本**两个文件都还在本机**
(10 个分叉文件的父文件无一缺失),所以本机能清干净。

**如实记下清不掉的情形**:如果父文件已经被删掉、只剩分叉文件,那么原件那一行的
`dedup_key` 永远回填不上(没有日志可读),副本那一行会带着自己的键留下 —— 重复
依旧。这种情形不比现在更坏(现在也是两条),但也修不好,因为判据在已经不存在的
文件里。Codex 不像 Claude Code 那样 30 天清日志,本机 610 个 rollout 最早可回溯到
项目起点,所以这是理论缺口而非当前损失。

### 3.5 那 629,518 个重复 token:删掉,不留标注

用户问的是清理还是标注。**选清理。**

标注(加一列 `dup_of`、让聚合查询排除)看起来更保守,但它把成本摊到每一个查询上,
而且漏掉过滤的那个查询会读到一条 `ts` 虚构、能落进任意时间桶的行 —— 面板上多出一
条 7 月 29 日的用量,而它其实是 7 月 17 日的。被删的行不是历史,是一次记账错误的
产物:它的每一个用量字段都能在保留下来的那行里逐字找到。

N6 保的是「数据独立于源日志生命周期」,不是「入库的行永不删除」。删除的判据完全在
库内(两行共享 `dedup_key`),可核实、可复现;删除条数写日志,与 ADR-0018 的重判
一样可审计。

## 四、被否决的方案

| 方案 | 否决理由 |
|---|---|
| 改 `event_id` 的依据 | 第二节:历史数据要么全库重复,要么把主键降级成可迁移列 |
| 解析器直接丢弃分叉文件的复制前缀 | 判据(前缀在哪结束)只能靠「行时间戳等于开文件时刻」这类启发式;更要命的是父文件不在时会**真的丢数据**,而键的方案在同样情形下仍会把这次生成记一次 |
| 只用 `total_token_usage` 作键 | 实测多出 1 次**同文件**碰撞 —— 少计,且不可见 |
| 只用 `turn_id` 作键 | 整数 `turn_id` 把 13 个无关会话合成一条 —— 同上 |
| `turn_id` + turn 内序号 | 序号依赖解析器行为,ADR-0004 后果一节已经点名这是现行方案的软肋,不该再引入一次 |

## 五、与既有决策的边界

- **ADR-0004**:`event_id` 的构造与幂等协议原样不变。本决策是在它之上**再加**一层
  约束,不是替换。解析器注释里与实测不符的那句一并改掉。
- **ADR-0013**(proxy 复用日志 id):方向正交。它解决的是同一次请求被两个通道看到、
  要认成同一行;这里解决的是同一次生成被写进两个文件。`dedup_key` 只有 codex 填,
  proxy 行恒为空,两者不会互相干扰。
- **ADR-0015 / ADR-0018 / ADR-0019**(device / provider / 设备合并):那三处都是
  「改一列、从不碰计数列」。**本决策不同:它会删行,计数会降。** 这是 CLAUDE.md
  白名单表之外的第一处,必须单独记一行,并写清它与那三处的区别 —— 那三处回答
  「这次请求算给谁」,本处回答「它被记了几次」,后者本来就是计数问题。
  安全边界是:删除只在**两行共享同一个 `dedup_key`** 时发生,永远只删其中一行,
  且删的是 `ts` 大的那条。判据在库内、可核实、与顺序无关。
- **ADR-0009**:`gen_ms` / `ttft_ms` 的计算不受影响。回放 turn 本来就被排除在区间
  之外,被删的副本上这两列恒为 0。

## 六、后果

- schema 加一列 `dedup_key` 与一个部分唯一索引;老库走 `ALTER TABLE`,存量行为空。
- `model.Event` 加一个字段,随 agent 协议一起传;字段是 `omitempty` 的可选项,
  旧版 agent 推上来的事件没有键,退化成只按 `event_id` 去重 —— 与今天等价。
- 本机执行一次 `serve -rescan` 完成回填与清理,预期删除 845 行、output 减少 629,518。
  这是**唯一一次**计数会下降;此后重扫恒为 0 变更,必须实测两遍验证。
- 覆盖率随 Codex 版本变化(旧版不写 `task_started`),与 ADR-0009 一样,不是固定值。
- 若将来 Codex 改掉 `turn_id` 的形态或不再逐字复制,键会自然退化成「不产出」,
  结果是回到今天的行为(可能重复),而不是误合 —— 失效方向是安全的。
