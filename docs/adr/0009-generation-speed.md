# ADR-0009 生成速度语义:生成区间与并集口径

状态:已采纳(2026-07-29,与用户确认)

## 背景

需求 F15(速度页)现有实现算出来的数不可信,而用户最初想要的恰恰是
「实时 token 速度 + 当前机器正在进行的会话的速度」。核查本机真实数据后
(claude-code 14,735 条 / codex 15,471 条样本)确认了三个独立的缺陷。

### 缺陷一:分母不是生成耗时

`duration_ms` 由 ADR-0006 定义为「到上一行任意日志记录的间隔」。那对**工作时长**
是正确的(工具执行也算投入),但拿它当**生成速度**的分母是错的 —— 速度的区间
必须是 `[请求发出 → 回复写入]`。

实测:claude-code 有 17% 的事件 `duration_ms > 30s`,那里面装的是人的思考与
工具执行时间,把速度算低了。

### 缺陷二:先相除再平均

`SpeedByModel` 逐条算 `output_tokens * 1000 / duration_ms` 再取均值/中位/P90。
比值的平均没有良好定义:单条 2ms 的事件就能贡献 466,000 tok/s,把 `avg` 拉到
137 而 `median` 只有 57。正确做法是**先求和再相除**。

### 缺陷三:Codex 排除得对,但理由是错的

`internal/store/speed.go` 注释称 Codex「`token_count` 间隔中位 30ms,是日志产物
而非生成耗时」。中位数确实是 30ms(claude-code 是 10,452ms),但**根因不是**
「写日志的间隔」。

真正的原因是:**rollout 文件会回放历史**。会话恢复时,Codex 把整段历史一次性
写入,时间戳用的是刷盘时刻而非事件发生时刻。实测一个 70 行的区块全部落在
`03:13:26.384/385` 这 1 毫秒内。统计最近 60 个 rollout:

| | 数量 | 占比 |
|---|---|---|
| 实时写入(时间戳与上一行不同) | 1,991 | 30.0% |
| 成批回放(与上一行同一毫秒) | 4,640 | **70.0%** |

所以 Codex 有 70% 的记录**根本没有可用的时间信息**。换任何区间取法都救不回来:
本次先按 `user_message` 取起点试过,回放块继承了很早以前那条真实 `user_message`
的时间,`gen_ms` 中位数变成 207,748ms(208 秒),比原来更离谱。

Claude Code 不存在这个问题:14,735 条样本里只有 7 条时长低于 1 秒。

### 并发是两层的

单纯换区间还不够,因为并发不止一层:

- **多会话并行**:同一台机器可能同时开着多个 Claude Code 会话;
- **会话内 subagent 并行**:subagent 日志写在 `<session>/subagents/*.jsonl`,
  带 `isSidechain: true` 且**沿用父会话的 sessionId**。本机一次会话观察到
  主线 520 条 assistant 记录 + 20 个 subagent 文件。

时长直接相加会重复计墙钟时间(两个会话各生成 10s,墙钟只过了 10s)。

## 决策

1. **新增 `gen_ms` 字段,与 `duration_ms` 并存**,不改后者语义(F8 依赖它)。
   区间起点按来源取「请求发出」标记:

   | 来源 | 起点 |
   |------|------|
   | Claude Code | 同文件内上一条 `type: "user"` 记录(工具结果也是 user 记录) |
   | Codex | **不产出 gen_ms** —— 70% 的记录时间戳是回放刷盘时刻,见上(2026-07-31 修订:改为按 turn 产出,起点不再取自日志行时间戳,见第 3 条) |

   沿用 ADR-0006 的 30 分钟 clamp。**按文件跟踪**是关键:subagent 各有自己的
   文件,天然就是独立的生成流,不需要额外的并发识别逻辑。

   Codex 维持排除,但换成有据可查的理由。将来若要支持,可行的方向是只取那
   30% 实时写入的记录(判据:时间戳与上一行不同),代价是覆盖率不全、且判据
   是启发式的 —— 值得单独评估,不在本决策内。

2. **速度 = Σoutput_tokens ÷ |生成区间并集|**,不是逐条比值再平均。
   - 单会话速度:在该 `session_id` 内部取并集;
   - 本机吞吐:该设备全部会话的区间取并集。

   三个会话各 50 tok/s 并行时,前者 50、后者 150 —— 两个都对,回答的是不同问题。
   与 ADR-0006 的「投入 union / 代理 sum」是同一个形状,复用 `unionMS`。

3. **Codex 纳入速度统计,但只认它自己记录的权威计时,不认日志行时间戳**
   (2026-07-31 修订;原文为「Codex 仍不纳入速度统计」「速度页必须显式说明
   『暂不覆盖 Codex』」,改动理由见文末「后续修订(2026-07-31)」)。

   turn 由 `event_msg/task_started` 与 `event_msg/task_complete` 按**文件位置**
   括起,生成区间取 `duration_ms − time_to_first_token_ms`,token 取区间内
   `info.total_token_usage` 的 output 增量。回放问题依旧存在,但这条路径不经过
   日志行时间戳,所以不受它影响。

   速度页必须显式标注 Codex 的 turn 覆盖率(实测 84.4%)与「含工具执行时间的
   保守下界」,而不是让用户以为看到的是全部用量,也不能把未覆盖的部分画成 0。

4. **历史回填改用 UPSERT**:`ON CONFLICT(event_id) DO UPDATE SET gen_ms = ...`,
   且仅在传入值 > 0 时覆盖,然后全量重扫一次。

   ADR-0006 当年的做法是「重建库全量重扫」,**现在不能再这么做**:需求 N6 要求
   数据入库后独立于源日志生命周期,而 Claude Code 日志 30 天清理、SSH 拉取的远端
   可能已不可达。重建会直接销毁超出保留期的历史。

## 与幂等铁律的边界

ADR-0004 的铁律是「同一条日志无论从哪条通道到达都只能计一次」。本决策**不触碰**它:

- `event_id` 的生成依据完全不变,`gen_ms` 不参与 ID;
- token 计数、成本、事件条数仍然只计一次,重扫不会让任何计数增长;
- 被改写的只有一个派生的时间字段,且只在原值缺失/新值有效时写入。

但要如实记下代价:**重扫从此不再是对既有行的纯只读操作**。以后再引入类似的
派生字段,应沿用同一模式(只补派生列、绝不改计数列),不要扩大到别的列。

## 后果

- 需要 schema 迁移加列;已入库的 53,880 条历史经一次全量重扫回填。
- 两个解析器都要改,单测一并更新;必须验证 `event_id` 对同一条日志不变。
- `SpeedByModel` 的逐条口径保留一轮作为对照,用真实样本比对新旧口径后再删。
- 速度页与实时页的口径需要显式标注:并集分母意味着「生成中的速度」,
  与燃烧速率(含空闲的墙钟速率)不是一回事,两者并列展示时不能混淆。

## 后续修订(2026-07-29)

**回填从未发生过。** 决策写了「然后全量重扫一次」,但当时没有任何入口能触发它 ——
位点存在状态文件里,而运行中的进程持有内存态,从外面改会被下一次提交覆盖。
真机核对:24,516 条 claude-code 事件里只有 493 条有 `gen_ms`,全部是解析器改完
之后新采的。

补的是 `serve -rescan` / `agent -rescan`:启动时清空位点,采集器起来之前完成重置。
见 `docs/configuration.md`。

同时要记下这条决策当时没说清的边界:重扫**只能补回日志还在的那部分**。
Claude Code 30 天清理日志,更早的事件按 N6 留在库里,但派生字段永远为空。
因此凡是基于 `gen_ms` 的视图都必须显示覆盖率,不能把「没有数据」画成「速度为零」。

**逐条口径已删除,对照结果记在这里**(决策第 3 条要求「比对后再删」)。
本机近 30 天 claude-opus-4-8:

| 口径 | tok/s |
|---|---|
| 旧:逐条比值取均值(分母 `duration_ms`) | 137.4 |
| 旧:先求和再相除(分母 `duration_ms`) | 31.0 |
| 新:先求和再相除(分母 `gen_ms` 并集) | 68.3 |

两个缺陷方向相反、同时存在:比值平均被 2ms 的小事件抬高一倍,而 `duration_ms`
作分母又因含思考与工具等待压低一半。

**并且日志通道不再给逐条中位数。** 换成正确的分母之后逐条比值仍然不可用 ——
区间里含等首 token 的时间,长回答无所谓,几个 token 的工具决策则几乎全是等待。
实测 claude-sonnet-5 有 69% 的响应不足 8 token,逐条中位被拖到 0.7 tok/s,
而整体是 57.6。把延迟与生成分开测是代理通道(F14)的能力,所以中位数与 TTFT
只留在那一列。

## 后续修订(2026-07-31):Codex 可以测了

**原文的测量成立,考察范围不完整。** 缺陷三说的是「rollout 会回放历史,时间戳是
刷盘时刻」—— 重新实测确认这条仍然对,而且口径要收得更紧:原文那张 70% 的表统计的是
**全部日志行**,而速度只关心 `token_count` 行。分开测,`token_count` 行的回放比例
是 **74.7%**,比原文更高;全部日志行反倒只有 32% 是回放。原文没说清这个口径差,
这里补上。结论不变:**沿日志行时间戳取生成区间这条路确实是堵死的**,不必再试。

被遗漏的是另外两条不经过日志行时间戳的路径:

1. **Codex 自己就记录权威计时。** `event_msg/task_complete` 携带 `turn_id`、
   `started_at`、`completed_at`、`duration_ms`、`time_to_first_token_ms`。这些值
   由 Codex 计算后写入,与它所在那一行的时间戳无关 —— 整块回放不会改写它们。
   `event_msg/turn_aborted` 同样带 `started_at` / `duration_ms`。
2. **按文件位置归属可以绕开回放。** `event_msg/task_started`(带 `turn_id`、
   `started_at`)与 `task_complete` 成对夹住一个 turn,`token_count` 记录顺序落在
   其间。回放是按原顺序整块写入的,**位置序保持不变**,所以按位置归属不受影响。
   注意 `token_count` 行本身**不带** `turn_id`,只能靠位置认。

### 实测(200 个 rollout)

| | 按时间戳窗口 | **按文件位置** |
|---|---|---|
| 可用 turn 覆盖率 | 38.5% | **84.4%**(944/1119) |
| 并集口径 tokens/s | 222.8(离谱) | **34.7** |
| 逐 turn 中位 / P90 | 56.2 / 2600.4 | **53.4 / 101.1** |
| 每 turn output 中位 | 8,742 | 6,235 |

`task_started` 1,131 条、`task_complete` 1,119 条,未配对仅 1 条 —— 配对本身是可靠的。
按时间戳窗口归属会把回放块里的记录塞进错误的 turn,于是同时压低覆盖率、抬高速度;
按文件位置两个数都回到合理区间。对照 claude-code 实测的 50–70 tok/s,34.7 的量级是
站得住的。

token 增量取 `info.total_token_usage` 的 `output_tokens + reasoning_output_tokens`
**逐条求差**,与现有 codex 解析器的 `deltaUsage` 语义一致。不要直接累加
`last_token_usage` —— 那会严重高估。

### 新口径的定义

- **turn 边界**:`task_started` / `task_complete` 按**文件位置**括起,不按时间戳。
- **生成区间**:`duration_ms − time_to_first_token_ms`,两个值都来自 `task_complete`。
- **token**:落在该区间内的 `token_count` 行的 output 增量之和。
- 并集与求和的规则沿用决策第 2 条,不因来源不同而改变。

### 必须如实标注的偏差:这是保守下界

`duration_ms − ttft` 里**含 turn 内的工具执行时间**,所以算出来的是速度的**下界**,
真实生成速度更高。34.7 低于 claude-code 的 50–70,主要就是这个原因,而不是 Codex
真的慢一半。展示时必须写明「含工具时间的保守下界」。

精化方向是扣掉工具区间 —— `event_msg/patch_apply_end` 与 `event_msg/mcp_tool_call_end`
都带 duration,可以从生成区间里减掉。**明确不在本轮**:先把量级正确的下界拿出来,
比先做精确更划算。

### 覆盖率与 TTFT

- **84.4% 的 turn 覆盖率必须在速度页显式呈现**,不能把未覆盖的部分画成 0。
  这是 2026-07-29 那次修订已经确立的原则(「没有数据」≠「速度为零」),
  Codex 泳道照样适用。
- **TTFT 是 Codex 直接给出的精确值**,不需要任何推算,也不依赖 turn 归属是否成功。
  实测中位 9,285ms、P90 26,842ms。它可以独立于 tokens/sec 先用起来 ——
  即便后续要精化生成区间,TTFT 这一列都不会变。

### 与幂等铁律的边界

不变:新增的 `gen_ms` / `ttft_ms` 都是**派生列,不参与 `event_id`**,ADR-0004 的
铁律不受触碰。历史回填沿用本 ADR 决策第 4 条的 UPSERT 模式 —— 只在新值有效时覆盖,
**绝不碰任何计数列**。一次 turn 算多快,和它被计几次是两回事。
