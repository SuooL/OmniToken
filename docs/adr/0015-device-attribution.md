# ADR-0015 设备归属:自报优先于旁观,以及采集起点

状态:已采纳(2026-07-30,与用户确认)。与 [ADR-0013](0013-proxy-log-same-request.md)
同类:细化 [ADR-0004](0004-event-identity.md) 在多通道下的落法,**不改动它的铁律**。

## 背景

多设备是实测出来的:把第二台 Mac(macmini)经 SSH 拉进真实库的一份拷贝,然后数。

- macmini 有 46,303 条真实事件(claude-code 19,772 + codex 26,531);
- 其中 **42,784 条(92%)库里早就有了,记在另一台机器名下**,真正新增的只有 3,519 条;
- 根因**不是** event_id 撞号,是两台机器的日志本身是**同步的**:543 个 codex rollout
  文件里 539 个文件名(含 UUID)逐字节相同;179 个 claude 会话文件里有 75 个两台
  都在,只是家目录不同(`/Users/hu/…` 与 `/Users/suool/…`);
- 混合之后的库里**重复 event_id 为 0** —— ADR-0004 经住了这次考验。

所以「只计一次」是对的,不许动:一次 API 请求就是一次扣费,它在几台机器的硬盘上
留下过几份日志,与厂商收几次钱无关。

缺陷在另一处:**设备归属退化成了「哪台机器先被扫到」**。`internal/store/store.go`
是 `INSERT OR IGNORE` 加几条定向填空,`device` 自插入那一刻起再没被动过。凡是同步过
家目录、恢复过备份、rsync 过日志的用户,拿到的设备维度都不可靠 —— 而他不会收到
任何提示。

## 决策

### 1. 归属分级:自报 > 旁观

新增一列 `device_origin`,只记一件事:这一行的 `device` 是怎么来的。

| 级别 | 通道 |
|---|---|
| `self` | 机器自己报的:`omnitoken agent` 推送、`serve` 扫本机日志、本机代理 |
| `observed` | SSH 拉取的镜像扫描 —— 设备名是照配置里的 ssh host 猜的 |

三条规则:

1. `observed` **永远不**覆盖已有归属;
2. `self` **可以**覆盖 `observed`,单向;
3. `self` **不**覆盖 `self` —— 先到的自报赢。

形状与 ADR-0013 那条 `source` 提升一模一样(一条守卫钉死的单向 UPDATE),理由也是
同一类:**跑这次请求的机器才是它的出处,另一台只是存了一份日志拷贝的旁观者。**

**第 3 条是启发式,不是地面真值,这里写明。** 它赌的是时序:真正跑的那台机器在秒级
内就把事件报上来,而同步过去的副本要先等文件同步、再等对面机器的采集周期,晚得多。
同步足够快、或原机器当时离线事后补报,它就会判错。选它是因为另外两个选项更差 ——
「后到者赢」会让归属随扫描顺序反复横跳,「谁都不许改」等于回到今天的先扫先得。

归属是**通道**的属性,不是事件的属性,所以它作为参数随批次传入
(`store.InsertEventsFrom(events, receivedAt, origin)`),不进 `model.Event`。
放进事件结构就意味着它会跟着 HTTP 推送过网,一个上报方就能自称任意级别;放在通道上,
级别由**收下这批数据的代码**决定,推送方无从伪造。`InsertEvents` 保持原样并按 `self`
委派 —— 走到那个入口的只有 agent 推送与代理,两者按定义都是自报。

### 2. token 计数一点没变

这次改动只决定一次请求落在哪个设备列下,不决定它算几次:

- `event_id` 的构造依据完全不变,`device` 与 `device_origin` 都不参与 ID;
- 覆盖名单上只有 `device` 一列,计数列一律不在其中 —— 与 ADR-0013 的填空守卫同样的
  纪律,回归测试盯着「三条规则下 token 都不许动」;
- 重复观测照旧是 `inserted = 0`。

### 3. 采集起点 `collect.ssh_hosts[].since`

按主机配 `"YYYY-MM-DD"`(本地时区零点),比它早的事件不从这台机器入库。留空/不配 =
不过滤,向后兼容;**边界那一刻算在窗口内**。日期写错直接拒绝启动,而不是当没配 ——
静默退化成「不过滤」恰好会灌进用户明确说不要的那段历史,而入库不可撤销。

理由不只是「用户说 macmini 从这周开始统计」:**加一台旧机器,不应该把它的历史整个
回灌成它的工作量** —— 那段历史可能本来就是别的机器干的(见背景那 92%),而它的归属
只是猜的。

位点照常推进到文件末尾:被窗口挡下的行是读过之后**主动丢弃**的,不是留到下次;
否则每一轮都要重读、重丢一遍。这不违反「offset 仅在上报成功后推进」——
那条铁律防的是丢数据,而这里是用户要求不要这些数据。

## 为什么不 把 device 加进 event_id

这是最直觉的修法,也正是 ADR-0004 的铁律要防的事故:同一次请求在两台机器的日志里
各算一行,token 计两遍,背景里那 42,784 条会当场变成 42,784 条重复。设备维度好看
不值这个价 —— 一次请求一次扣费,这一条不让步。

## 为什么不 只写进文档当已知限制

因为踩中的人不是少数:iCloud 同步家目录、rsync 日志、从备份恢复、开发机与构建机共用
一套 dotfiles,任何一种都会让设备维度出错,而面板上看不出任何异常 —— 它只会安静地
把一台机器的活算在另一台头上。要把这个当作**可分发的开源产品**来做,就不能把
「这个维度可能是错的」留给用户自己去发现。代价也小:一条与 `source` 提升同形的单向
覆盖,加一列。

## 为什么不 让 SSH 拉取也算自报

诱惑在于:配置里明明写了那台机器叫 macmini,拉的也确实是它硬盘上的日志。但这只能
确认「这份日志在那台机器上」,不能确认「这次请求是在那台机器上跑的」—— 背景里的
42,784 条就是现成的反例。旁观就老实标成旁观,别把配置里的一句声明当成证据。

## 后果

- **拉取不等于自报。** 只被 SSH 拉取的设备,归属仍然靠第 3 条那个先到先得的启发式:
  两台机器都只被拉取、日志又是同步的,谁先被扫到谁拿走这批事件。想要准确的设备维度,
  **每台机器上都得跑 agent**。这句必须说白,不能让人以为配了 `ssh_hosts` 就等于把设备
  分清楚了。
- 迁移后的历史行一律读作 `observed`(而不是 `self`):事后没有任何办法判断它们当初
  是谁跑的,而 `observed` 是后来的自报还能纠正的那一级。代价是第一次在某台机器上跑起
  agent 时,会有一大批历史行被改到它名下,日志里能看见
  `N existing events re-attributed`。改的只有 `device` 一列。
- 写入路径多一条 UPDATE,只在「这一行已存在 + 本次是自报」时执行;新行走 INSERT,
  不受影响。
- `since` 是个一次性的选择:窗口外的事件丢掉之后位点已经推过去了,以后想要就得
  去掉 `since` 再 `-rescan`,而且只能捞回远端日志还在的那部分(Claude Code 30 天清理)。
- 这一列目前只在存储层生效,面板还不区分「自报」与「旁观」。等到有人需要判断某台机器
  的数字可不可信时,把它露出来是自然的下一步 —— 本决策不做。
