# ADR-0013 同一次请求被日志与代理同时观测

状态:已采纳(2026-07-30,与用户确认)。细化 [ADR-0004](0004-event-identity.md) 的
事件身份在多通道下的落法;不改动它的铁律本身。

## 背景

F14 的本地代理原本假定它采的是「API 直调」—— 用户自己写的脚本,那些不落日志的
流量。但没有任何东西拦着把 Claude Code 指过来,而 ADR-0011 之后我们恰恰有了
把订阅工具指向代理的动机:**只有代理能测出 TTFT**,日志里根本没有这个字段。

一指过去就会重复计数,代码级可确认:

- 日志事件 id 是 `cc:<message.id>:<requestId>`(`parser/claudecode/parser.go`);
- 代理事件 id 是 `px:<sha1(设备|前缀|起始纳秒|序号)>`;
- 所有总量查询对全部 source 求和,**没有任何跨通道去重**。

同一次请求于是入库两行,token 计两遍。这正是 ADR-0004 要防的那类事故,只是它
当时只考虑了「同一条日志经不同传输通道到达」,没考虑「同一次请求被两种观测手段
各看见一次」。

## 决策

### 1. 能认出同一次请求时,两边产出同一个 event_id

代理对第一方 Anthropic 流量产出与日志**完全相同**的 id,让 ADR-0004 既有的幂等
机制把两次观测收敛成一行,不需要任何新的去重逻辑。

原料两边都有,已在真机核对:

| 部件 | 日志侧 | 代理侧 |
|---|---|---|
| `message.id` | `message.id`(`msg_01…`) | SSE `message_start` 的 `message.id`,非流式则是响应体顶层 `id` |
| `requestId` | `requestId`(`req_011C…`) | 响应头 `request-id` |

两者格式一致(`req_011C…` 就是 Anthropic 的 `request-id`),所以
`cc:<message.id>:<request-id>` 在两侧算出来是同一个字符串。

**认不出就退回 `px:`**。OpenAI 与自定义上游没有同样的共享键,非流式响应也可能
没有这两个字段;那些是独立观测,没有孪生行,退回原来的 id 是正确的。

代理**不会**因此谎称自己是别的来源:脚本直调 Messages API 同样带 message.id 与
request-id,也会拿到 `cc:` 前缀的 id。这无害 —— 没有孪生行时,去重本来就不发生。

### 2. 一行事件由两次互补的观测拼成

两个通道看见的是同一次请求的不同侧面:

| 只有日志知道 | 只有代理知道 | 两边一致 |
|---|---|---|
| session_id、cwd、repo、git_branch、app_version | ttft_ms、精确生成区间、account_label | token 四分量、模型 |

token 两边必然相同 —— 它们读的是同一个 API 响应里的同一个 usage 块,所以先到先
写不会产生分歧。

规则:**先到的建行,后到的只允许填空,不允许覆盖。** 这是 ADR-0009 那条
`gen_ms` 回填的推广,从一列扩到一组明确列出的列,并显式排除计数列。可填的是:
`gen_ms`、`ttft_ms`、`session_id`、`cwd`、`repo`、`git_branch`、`app_version`。

**`duration_ms` 只有日志能写。** 它在 ADR-0006 里的语义是「到上一条日志记录的
间隔」,F8 工时依赖这个语义;代理测出的生成耗时是另一个量,写进去会污染工时,
所以代理在共享行上不写这一列,它的测量值只进 `gen_ms`(那本来就是生成区间)
与 `ttft_ms`。但日志侧仍要能填 —— 代理先建的行如果连日志的间隔也拒之门外,
被代理的请求就会整批掉出工时统计。守卫因此是「来源不是 proxy 且原值为 0」。

(这一条最初写成「任何人都不许填 duration_ms」,真机跑通后发现工时会被打穿,
当场改成现在的写法。)

### 3. source 归工具,不归观测手段

代理几乎总是先到(请求一结束就发,而采集器有一个轮询间隔的滞后),照「先到先写」
它会赢下 `source`,于是开了代理之后 Claude Code 的用量会突然记成 `proxy`,
「按来源」的历史就此断成两截。

所以给一条**单向**的例外:同一 id 的行上,日志来源可以把 `source` 从 `proxy`
改写成自己,反向绝不允许。理由是工具才是这次请求的来源,代理只是我们看见它的
方式。这条例外被守卫钉死在 `source = 'proxy'` 上,只会发生一次,且永远不碰计数列。

## 边界:不得影响既有网络分流

代理只增加一跳环回。上游连接的目标主机与 SNI 不变,所以**按域名分流的规则照常
命中**;TUN 抓的是 IP 层而 127.0.0.0/8 走 lo0,本地那一跳分流看不见也不需要看见。

唯一会失效的是**按进程匹配**的规则(`PROCESS-NAME` / `PROCESS-PATH`):发起连接的
进程从 `claude` 变成 `omnitoken`。这一条必须写在文档里(已写入
`docs/configuration.md`),补一条指向同一策略组的 `PROCESS-NAME,omnitoken,<组>`
即可。

代理**默认关闭**,不配 `proxy_listen` 就完全不存在。

## 边界:不得违反厂商用户政策

这条以前没有明文,借这次定下来,适用于代理的全部演进:

- **纯透传**:不改写请求与响应的任何内容,不重试,不注入或剥离鉴权,不缓存或
  转存凭据(只留 SHA-256 指纹前 12 位);
- **不自行发起请求**:代理永远不会用用户的凭据向厂商发任何它自己的调用。
  ADR-0011 已经因为相近的理由把配额从「调 OAuth 端点」改成「捕获 Claude Code
  自己递出来的载荷」,同一条底线在这里继续成立;
- **不绕过任何限制**:不做多账号复用、不做限流规避、不做配额探测;
- **只采元数据**:永不读取对话内容(需求 N4),解析只取 usage 与时间;
- **只作用于本机、本人、本来就要发出的流量**:环回监听,默认关闭,用户显式指向
  才生效。

代理是对自己流量的**被动观测**,不是一层中间人服务;上面每一条都是为了让它保持
这个性质。任何会让它开始「代表用户做事」的改动,都要重新过这一节。

## 后果

- 开代理不再重复计数,而且能同时拿到日志的 repo 归属与代理的 TTFT —— 这是任何
  单一通道都给不出的一行数据。
- `InsertEvents` 从「只回填一列」变成「回填一组列」。风险面确实变大了,守卫因此
  写死:只填空、绝不覆盖、计数列一律不在名单里,并有回归测试盯着「重复观测不改
  变任何计数」。
- OpenAI / Codex 侧没有共享键,把它们指向代理**仍会重复计数**。文档必须明说,
  这个 ADR 不解决那一半。将来若要解决,方向是 rollout 里是否存在可与响应头对上的
  标识,需要单独核对,不在本决策内。
