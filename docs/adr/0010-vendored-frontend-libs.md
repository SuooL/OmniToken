# ADR-0010 前端可用 vendored 预构建库(修订 ADR-0002)

状态:已采纳(2026-07-29,与用户确认)。修订 [ADR-0002](0002-tech-stack.md) 的前端条款。

## 背景

ADR-0002 定的是「前端 vanilla JS + SVG,零运行时依赖、零构建链」,并明确写下代价:

> 放弃了 npm 图表生态,图表手写 SVG

用户复盘面板视觉时指出「UI 过于原始静态、图像丰富度不够」—— 不满意的正是当年
主动牺牲掉的那部分。

讨论中我给出过一个**错误论证**:称 headless 机器没有外网所以不能用现成库。这是把
前后端搞混了 —— headless 机器跑的是 `omnitoken agent`,只采集上报,**从不渲染面板**;
面板由 `serve` 提供、在有 UI 的机器的浏览器里打开。headless 的网络状况与前端技术栈
无关。同样,「scp 一个文件」的部署优势也与前端技术栈无关:构建产物照样
`go:embed` 进同一个二进制,运行时仍是单文件。

去掉这些错误论证后,真实的取舍只剩一条:**要不要在开发机与 CI 引入 Node 构建链**。

## 决策

**允许把预构建的第三方库产物直接 vendored 进 `web/vendor/`,但不引入构建链。**

浏览器 `<script>` 直接加载,`go:embed` 打进二进制。既拿到成熟库,又保持:

- 零构建:`make build` 仍然只是 `go build`,贡献者不需要装 Node;
- 离线可用:不依赖 CDN,查看端不需要外网;
- 单二进制分发不变。

首个 vendored 库:ECharts 6.1.0(Apache-2.0),用于替换手写 SVG 图表。取完整包
而非精简包,因为日历热力图不在精简包里。

## 规矩

1. **只收预构建产物**,不收源码树、不收 `node_modules`。
2. **必须核对校验和**:从 npm registry 的 `dist.integrity` 取 sha512 比对,不一致就停。
3. **必须记录来源**:`web/vendor/README.md` 写清来源 URL、版本、许可与升级步骤;
   随附上游 LICENSE 原文。
4. **许可须兼容**:只收 MIT / Apache-2.0 / BSD 这类宽松许可。
5. **克制**:每加一个库都要能说清它替代了多少手写代码。库不是免费的 ——
   它进仓库、进二进制、要人工升级、出了 CVE 要人工响应。

## 后果

**正面**

- 图表拿到成熟实现:渐变、动画、悬停、日历热力图、缩放,不用逐个手写 SVG。
- ADR-0002 的其余部分(Go 无 CGO 单二进制、SQLite、serve/agent 同一二进制)全部不变。

**负面**

- 二进制增大约 1.1MB(17MB → 18MB),可接受。
- 升级靠手工换文件,没有 `npm audit` 之类的自动化。规矩 2 与 3 就是为此而立。
- 仓库里多了压缩过的第三方代码,`git diff` 对它无意义 —— 升级 PR 必须在描述里
  写清版本与校验和,而不是让 reviewer 去读 diff。

## 没有选的路

- **引入 Node + Vite + 组件库**:UI 上限最高,但要重写 ADR-0002 的定位、迁移九个
  页面、让 CI 与贡献者都装 Node。当前需求(更好的图表与图标)用 vendored 库就能
  满足,不值得为此换掉整条工具链。将来若要做复杂交互(拖拽编排、虚拟长列表)
  可以再议。
- **继续全手写**:上限太低,且正是本次不满意的来源。
