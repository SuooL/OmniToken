# ADR-0034 窗口余量改为锚在当前窗口的官方百分比上,历史估计退居先验(修订 0025)

状态:已采纳(2026-09-07,与用户确认)

## 背景

[ADR-0025](0025-quota-capacity-estimate.md) 用跨窗口取样学「一个窗口装多少 token」,
取最近 30 个合格窗口的 25 分位。那个决定解决的是「不要凭当前窗口的瞬时比值编一个
精确得吓人、实际在两倍区间里漂的数字」,这个顾虑今天依然成立。

但它把答案放错了地方。2026-09-07 面板上同时显示:

```
CLAUDE · 官方配额
11%  32M
5h · 还剩 67M · 3h18m
```

**已用 11%、已消耗 32M,却说只剩 67M。** 这两个数差 2.6 倍,而且矛盾是显而易见的:
32M 是 11%,那 100% 就是 290M 上下,不可能只剩 67M。

查库看清了原因。claude-code 五小时窗口最近的样本换算出来的容量:

| 窗口(reset) | 峰值 | 该窗口 token | 隐含容量 |
|---|---|---|---|
| 09-07 12:10 | 38% | 94.8M | 249M |
| 09-06 23:30 | 30% | 72.3M | 241M |
| 09-06 18:20 | 92% | 131.9M | 143M |
| 09-06 13:20 | 52% | 37.7M | **72M** |
| 09-05 19:00 | 95% | 67.0M | **70M** |
| 09-04 15:00 | 50% | 81.3M | 163M |

同一周之内,相邻窗口之间差 3.5 倍。25 分位于是落在最低那一批上,给出 99.5M ——
**对「典型窗口」也许不算离谱,对「屏幕上这个正在用的窗口」就是错的**。

关键在于:旁边那个百分比是**官方给的权威数字**(ADR-0007 的铁律「权威优先」)。
一个推断值和它并排显示却对不上,不管推断得多讲究,读它的人只会得出「这个面板在
瞎编」的结论 —— 而且这次它确实错了。

## 决策

### 1. 余量锚在当前窗口自己的 token/百分比 比值上

`live = 当前窗口 tokens ÷ (pct ÷ 100)`。屏幕上写「已用 11%、32M」,那么
「还剩」就必须约等于 `32M × 89/11`。这是自洽的最低要求。

### 2. 历史估计不丢,降为先验,按可靠度加权

两个误差项里,只有一个是能量化的:

- **live 的量化误差**:官方只给整数百分比,读数 `pct` 天然带半个点的舍入,
  相对误差 `0.5/pct` —— 1% 处 ±50%,30% 处 ±1.7%;
- **先验的误差**:拿别的窗口的额度来回答这个窗口,代价就是 ADR-0025 实测的
  跨窗口变异系数 **26%**。

按方差倒数加权:

```
w = pct² / (pct² + (0.5/0.26)²)     # (0.5/0.26)² ≈ 3.70
估计 = w · live + (1−w) · 先验
```

于是:pct=1 时 w=0.21(先验主导),pct=2 时 w=0.52(势均力敌),
pct=10 时 w=0.96,pct=40 时 w=0.998(当前窗口主导)。

**这不是把 ADR-0025 推翻,是给它划定作用域**:它回答的「典型窗口有多大」在窗口
刚开、百分比还没有分辨率的那段时间是唯一能用的信息;一旦官方百分比本身足够粗
到可以做除法,就该听它的。

### 3. 没有先验时,窗口够深就自己回答

ADR-0025 §5 规定样本不足 3 个就什么都不显示。那对**新装的机器**过于苛刻:
五小时窗口要凑够三个合格样本得等一天,而官方每几秒就在告诉你答案。
改为:没有先验时,`pct ≥ 10%` 就用 live 单独回答(此时舍入误差 <5%);
低于 10% 且没有先验,仍然什么都不显示 —— 编一个数比不给更糟,这条不变。

### 4. 取样搬到写入路径,不再由渲染触发

原来 `ObserveCapacity` 是在 `buildWindowCards` 里调的,也就是**有人打开面板才会取样**。
两个后果:窗口在没人看的时候涨满,估计学不到任何东西;而 ADR-0028 的响应缓存
又把剩下的大部分请求挡掉了。顺带,一个 GET 会写库本身就不该。

改为挂在 `Store.InsertQuotas` 上:快照从哪条路进来(本机扫描、agent 推送、SSH 镜像),
校准就跟着更新,调用方想忘也忘不掉。这就是「变动的时候定时测算」。

**开销控制**:`ObserveCapacity` 只升不降,所以先做一次极便宜的查询取该窗口已记录的
峰值,读数不高于峰值就直接返回,不去扫事件。快照每几秒一条,而百分比一个窗口最多
涨一百次,昂贵的那半就只跑那么多次。

### 5. 作废 codex 已有的容量样本

ADR-0033 之前,改名的 codex provider 被归成第三方中转,于是每个窗口的分子接近 0,
样本长这样:`peak=100% / tokens=0.53M` → 一个五小时窗口装 0.5M。这些样本**自己好不了**:
`ObserveCapacity` 不许降低峰值,100% 的行会一直卡到滚出 30 窗口的记忆 —— 周窗口就是半年。

用一次性迁移 `migrateCodexCapacitySamples` 删掉(只删 `source='codex'`),
下次启动的 `backfillCapacity` 从 `quota_snapshots` + 事件重建。
**这张表不含任何计数**,是从快照和事件推导出来的校准,删了能重建 —— 与「唯一会让
计数下降的操作」(ADR-0020)不是一回事。

## 后果

- 面板上「已用 X%」与「还剩 Y」从此自洽。用户看到的 95% 窗口会诚实地显示所剩无几,
  而不是拿一个典型窗口的额度去安慰他。
- 先验的作用域收窄到窗口前 10%。ADR-0025 的取样、30% 入选门槛、25 分位全部保留 ——
  它们决定的正是先验本身的质量。
- `fillCapacity` 变成纯读,`buildWindowCards` 不再写库(加了单测钉住)。

## 局限

`live` 仍然假设**这个窗口剩下的部分与已消耗的部分构成相似**(模型配比、缓存读占比)。
ADR-0025 实测过官方计量不是本机任何 token 口径的线性函数,所以窗口内也会漂
(实测从 880M 漂到 470M)。区别在于:现在漂的方向和屏幕上的权威百分比是一致的,
而不是各说各话。真要更进一步,得先能解释官方计量到底在数什么,那是另一回事。
