# ADR-0021 聚合时区:把日界钉在配置里,而不是主机设置上

状态:已采纳(2026-07-31,与用户确认)

## 背景

「今日用量」「30 天趋势」「热力图」「周/月报表」全都要把一个 epoch 毫秒切成日历天。
切在哪里,取决于时区。

实测本机(Hub 在 `America/New_York`,另一台设备在 `Asia/Shanghai`,两机时钟同步、
epoch 完全一致,只是显示时区不同):

| Hub 时区 | 同一时刻的「今日」事件数 |
|---|---|
| `America/New_York` | 1,954 |
| `Asia/Shanghai` | 4,109 |

**同一份数据,差 2 倍多。** 这不是显示差异,是统计口径。

日界现在在两处独立计算,都跟随**运行 Hub 的那台主机的系统时区**:

- Go 侧 9 处 `time.Date(..., now.Location())`;
- SQLite 侧 8 处 `date(ts/1000, 'unixepoch', 'localtime')`。

两条路目前**是一致的**(已用真实库验证:同一时刻两者给出的今日事件数相同),
因为 modernc 的 SQLite 驱动把 `'localtime'` 实现为 Go 的 `time.Local`。这一点是
本决策能成立的前提,也是它的隐含依赖 —— 换驱动要重新验证。

真正的问题是这个口径**隐式**:它等于主机的系统设置。改一次系统时区(出差、
重装、容器默认 UTC),全部历史日聚合会静默平移一整天,而面板上没有任何迹象。

## 决策

**1. `config.json` 新增 `timezone`,取 IANA 名(如 `America/New_York`)。**

加载时用 `time.LoadLocation` 校验,**非法即拒绝启动**。实测 `LoadLocation` 对
未知时区返回 error 而不是静默回落,所以这条能守住 —— 与 ADR-0015 对 `since` 的
处置同形:畸形配置宁可启动失败,也不静默降级成另一种口径。

**2. 生效方式是进程内赋值 `time.Local`,不是给 17 处调用点传 Location。**

这是本决策唯一有争议的地方:`time.Local` 是包级全局变量,改它影响整个进程。
选它的理由:

- 它是**唯一**能同时管住两条路的开关。给 Go 那 9 处传 `*time.Location` 解决不了
  SQL 那 8 处的 `'localtime'`;要让 SQL 跟上就得把 8 条 SQL 改成显式偏移量,而
  偏移量随夏令时变化,等于自己重实现一遍时区库。
- 赋值发生在**启动早期、任何查询与格式化之前**,此后只读。不存在并发写。
- 替代方案(给每处传 Location)要改 17 个调用点、且**没有机制阻止第 18 处忘记传**,
  而忘记的后果是那一个视图的日界与其余的不一致 —— 比全局变量更难发现。

**3. 留空 = 跟随主机系统时区,但启动日志必须打印解析结果。**

不强制配置:headless 服务器零维护是 N1 的要求,多一个必填项就多一道部署摩擦。
但「跟随系统」从此是一个**被明确记录过的选择**,而不是没人注意到的默认。

## 代价与边界

- **改这个值会重新解释全部历史。** 事件的 epoch 不变,但它们落在哪一天会变。
  这不是数据迁移,是口径变更 —— 改之前应该清楚自己在改什么。
- **只作用于 Hub。** agent 只推送 epoch 毫秒,不做日界切分;statusline 读的是
  Hub 已经算好的数。所以单点配置就够,不需要每台机器都设。
- **不做「按设备各自时区分别聚合」。** 跨设备求和必须落在同一根时间轴上,
  否则「今日总量」无法定义 —— 与 roadmap「明确不做:多币种」是同一个理由:
  聚合视图必须单一口径。
- **依赖 modernc 驱动把 `'localtime'` 实现为 `time.Local`。** 这一条已实测,
  但它是驱动的实现细节而非 SQLite 的规范。换驱动或升级大版本时要重跑那个验证。
