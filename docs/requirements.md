## 1. 背景与问题

用户在多台机器(以 headless Linux 服务器为主,少量 macOS GUI 机器)上使用
LLM 编码工具(Claude Code、Codex 等)及直接 API 调用。现有工具的缺口:

- **ccusage**:单机、事后单次统计,无多机汇集、无实时、无速度指标;
- **token-monitor**:有多机 hub 与实时,但 Electron 桌面形态与服务器环境错配,
  hub 只同步摘要级数据,无事件级中心存储,无速度指标,无 API 直调采集。

## 2. 目标与非目标

**目标**:个人使用的、跨设备的 LLM 用量监控与分析系统,事件级数据完全自持有。

**非目标**:多租户/团队权限体系;网页端(claude.ai 等)订阅用量(拿不到数据);
替代计费系统(统计口径以工具日志与代理观测为准)。

## 3. 干系人与使用场景

单用户,N 台设备。GUI 机器(或任意浏览器,含手机)作为统一查看入口;
服务器只需被统计、零维护成本优先。

## 5. 非功能需求

- **N1 部署形态**:采集端与展示端分离;服务器侧无 GUI 依赖;单二进制、无 CGO、
  可交叉编译;查看端仅需浏览器。
- **N2 网络拓扑无假设**:不要求公网 IP、不强制装组网软件;agent 仅出站;
  "机器 d 只能经 c 访问"须支持(中继)。
- **N3 可靠性**:断网不丢数据(日志即重传缓冲,offset 仅在上报成功后推进);
  服务端重启/状态损坏可全量重扫自愈(依赖 F4)。
- **N4 隐私**:只采集用量元数据,永不采集对话内容;数据仅存于用户自己的机器。
- **N5 数据规模**:单用户十万级事件/月,SQLite 单文件足够;查询响应 < 1s。
- **N6 历史保全**:数据入库后独立于源日志生命周期(Claude Code 默认 30 天清理)。

## 6. 验收基准(节选)

- 首次部署导入历史后,面板数字与 ccusage 同期统计可对账(F7 定价对齐后);
- 新增用量在采集间隔(默认 15s;SSH 拉取 ≥60s)内出现在面板;
- 同一日志被本地扫描与 agent 推送双通道观测,入库计数不变(F4,已实测验证)。
